## 问题
Memory 目前只有设计文档，没有实体、业务逻辑、持久化实现、REST 路由或 MCP 工具。项目需要先冻结它要解决的问题和边界，再决定数据模型与接口，避免把 Agent 的临时上下文、跨项目通知或代码百科重复实现为“记忆”。

## 方案
1. **Memory 只保存需要跨会话继续遵守的决策性知识。** 记录内容包含标题、Markdown 正文、决策原因、适用范围、优先级、来源项目和标签；临时对话、文件内容与执行日志不进入 Memory；
2. **写入由 Agent 或用户显式触发。** 系统不从会话自动抽取记忆，避免未经确认的推断变成长期约束；
3. **生命周期采用 `active`、`deprecated`、`archived`。** 默认查询只返回 `active`；被替代的记录进入 `deprecated` 并保留历史；仅作留档的记录进入 `archived`；
4. **PostgreSQL 保存完整卡片、标签及关联关系。** Redis 只在真实查询负载证明有必要后用于热点缓存，不作为首版正确性依赖；
5. **Memory 保持独立业务域。** 它不直接调用 RepoWiki、Q&A、Pin 或 Preview；Agent 通过 MCP 组合这些能力；
6. **首版提供显式创建、条件查询、详情读取、更新和删除能力。** REST API 供控制台使用，MCP 工具供 Agent 使用；接口命名和请求结构在实现前以当前工程规范重新确认，不直接复制旧 Wiki 的参考值。

## 不做什么
- 不自动把每轮对话写成记忆——噪声会淹没真正需要长期遵守的决定；
- 不把 Memory 做成跨项目消息队列——定向通知和 FIFO 消费属于 Pin；
- 不存储代码文件或生成的 Wiki 页面——代码知识读取属于 RepoWiki；
- 不在首版加入向量数据库——现有需求可先由结构化过滤和 PostgreSQL 文本检索验证；
- 不让 `accepted` 状态等同于“代码已部署”——文档共识与实现状态必须分开记录。

## 备选

| 方案 | 否决原因 |
| --- | --- |
| 自动从所有会话提取记忆 | 无法可靠区分临时信息、猜测和已确认决定 |
| 复用 Pin 表保存记忆 | Pin 的一次性消费语义与长期检索、废弃和归档语义冲突 |
| 直接把 ADR 文件当运行时 Memory | ADR 适合仓库内长期决策，但不能满足跨项目条件检索和 MCP 写入 |
| 首版引入向量数据库 | 增加部署与一致性成本，尚无检索质量数据证明必要 |

## 待定
- 标签采用独立实体还是 PostgreSQL 数组——阻塞数据模型设计；
- 删除采用物理删除还是软删除——阻塞审计与保留策略；
- 关键词检索采用 PostgreSQL 全文索引还是首版 `ILIKE`——不阻塞领域边界评审，阻塞性能验收标准；
- 来源项目是否必填——不阻塞提案评审，需结合全局记忆场景确认。
